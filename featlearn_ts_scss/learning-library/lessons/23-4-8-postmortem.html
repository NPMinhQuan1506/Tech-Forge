23.4.8. Postmortem

Understand Postmortem from its purpose and simplest model to its internal behavior, trade-offs, debugging signals, and production use.

01 · Orientation

What you will learn

By the end, you should be able to explain Postmortem without jargon, draw its smallest useful model, recognize it inside a production service deployed, monitored, and changed by a team, and choose evidence that confirms whether it works.

Prerequisite check

You only need the chapter idea: Resources, queues, contention, bottlenecks, profiling, logs, metrics, traces, dashboards, alerts, and incidents. If a term is unfamiliar, keep reading; the first example builds the model from ordinary experience.

  • State the problem the concept addresses.
  • Identify input, internal state, operation, output, and failure boundary.
  • Compare at least two implementation choices.
  • Verify a claim with observable evidence.

02 · Core theory

Start with the idea, not the jargon

A plain-language definition

Postmortem is the focus of this lesson inside Observability. Its technical meaning comes from the role it plays in this mechanism: Performance work connects user-visible latency and throughput to constrained resources. Observability correlates logs, metrics, and traces so an engineer can move from a symptom to the responsible request, dependency, and line of work.

Why this concept exists

The practical reason to study Postmortem is to predict behavior rather than memorize a label. Averages hide tail latency, high-cardinality labels overwhelm telemetry, or measurement changes the workload. Understanding the contract, internal state, and observable evidence lets an engineer isolate that failure instead of guessing.

A familiar comparison

Think of Postmortem like operating a city: architecture defines districts, delivery builds roads, security sets boundaries, and observability provides sensors. The comparison is intentionally incomplete, but it gives you a first picture. After that picture is clear, replace each familiar object with the real technical component and follow the data step by step.

The technical core

Performance work connects user-visible latency and throughput to constrained resources. Observability correlates logs, metrics, and traces so an engineer can move from a symptom to the responsible request, dependency, and line of work.

Place Postmortem inside that mechanism and trace one concrete unit of work through it. Name the representation at every boundary, the state that persists, and the rule that changes it. This is the point where a memorized term becomes an engineering model.

Do not stop at the analogy

A common mistake is to learn Postmortem as an isolated definition. In a real system it participates in a chain: User symptom → Service metric → Distributed trace → Resource bottleneck. Its value and its failure modes only become clear inside that chain. An analogy helps you enter the topic; measurements and concrete behavior tell you where the analogy ends.

03 · Visual model

Follow the information

The middle boxes separate the public idea from its implementation. Users care about the contract: valid input should produce a predictable result. Engineers must also understand the mechanism because resource limits, concurrency, invalid state, and partial failure can change that result.

04 · Examples

See the concept at three levels

Everyday comparison

Use a familiar system

Imagine operating a city: architecture defines districts, delivery builds roads, security sets boundaries, and observability provides sensors. Identify the thing being requested, the rule that decides what happens, the place where state is stored, and the signal that tells you the work succeeded. That structure is the bridge to Postmortem.

05 · Under the hood

What actually happens

Performance work connects user-visible latency and throughput to constrained resources. Observability correlates logs, metrics, and traces so an engineer can move from a symptom to the responsible request, dependency, and line of work.

  1. User symptom: Identify the exact input and representation entering Postmortem.
  2. Service metric: Apply the rules and constraints that define Postmortem.
  3. Distributed trace: Follow state changes, resource use, and calls across the implementation boundary.
  4. Resource bottleneck: Verify the outcome with tests, build artifacts, deployment history, metrics, traces, logs, and incident timelines.

Questions an engineer asks

Who owns the state? What is the unit of work? Which operation can be repeated safely? What happens when execution stops halfway? Where is the slowest boundary? Which guarantee is essential, and which is merely convenient?

Trade-offs

SimplicityFewer moving parts are easier to explain and debug.
PerformanceExtra indexing, caching, parallelism, or specialization can reduce time but add state.
CorrectnessStronger validation and guarantees cost work but prevent ambiguous results.
OperabilityLogs and measurements cost storage and attention but shorten investigations.

06 · Guided practice

Build the smallest observable version

Exercise A — explain and draw

  1. Write a two-sentence definition of Postmortem for a learner who has never seen it.
  2. Draw four boxes: input, state, operation, output.
  3. Add one success path and one failure path.
  4. Circle the first boundary you could measure or log.

Done when: another person can follow the drawing without needing you to explain missing arrows.

Exercise B — make a primitive

  1. Create a tiny program, command sequence, table, or paper simulation for Postmortem.
  2. Use one normal input, one boundary input, and one invalid input.
  3. Record tests, build artifacts, deployment history, metrics, traces, logs, and incident timelines before and after each run.
  4. Change one assumption and predict the result before running again.

Done when: you can point to evidence that supports or disproves your prediction.

Exercise C — break it on purpose

  1. Remove a required input or dependency.
  2. Repeat an operation that may not be safe to repeat.
  3. Increase the workload until a limit becomes visible.
  4. Improve the error so it tells the next engineer what failed and where to look.

07 · Real-world problem

Investigate a failure under pressure

Scenario: a team responsible for changing software without surprising its users reports a failure related to Postmortem. Averages hide tail latency, high-cardinality labels overwhelm telemetry, or measurement changes the workload. The first explanation sounds plausible, but the team has not yet located the earliest broken boundary.

Your task

  1. Define the expected behavior and the affected unit of work.
  2. Collect a good case and a bad case with the same observation points.
  3. Find the earliest step where their state diverges.
  4. Form three hypotheses: input, mechanism, and dependency.
  5. Run the cheapest test that can eliminate one hypothesis.
  6. Propose a fix, a regression check, and one production signal.

Decision record

Write five short lines: context, evidence, decision, trade-off, and follow-up. This turns an isolated fix into reusable engineering knowledge.

08 · Extension

Connect it to the larger system

Revisit Postmortem at three scales. At micro scale, inspect one operation and its state. At component scale, identify its callers and dependencies. At system scale, ask how traffic, failure, security, cost, and team ownership change the design.

  • Compare: find another technique in Observability that solves a similar problem. Write when you would choose each.
  • Measure: choose a metric for speed, capacity, accuracy, reliability, or maintainability and explain why it represents user impact.
  • Teach: make a one-minute explanation using one analogy, one diagram, and one counterexample.
  • Use AI carefully: ask an AI tool for three failure modes, then reproduce or reject each using documentation, a test, or direct observation.

09 · Self-check

Can you explain it without the page?

1. What problem does Postmortem solve?

A strong answer names the situation before the concept, the cost of leaving it unsolved, and the guarantee or capability the concept adds.

2. Where does state live, and how does it change?

Name the owner of the state, the operations allowed to change it, and the evidence that a change completed.

3. What is one misleading simplification?

Explain where the everyday analogy stops matching the technical mechanism.

4. How would you debug a failure?

Start from the expected contract, compare a good and bad case, and locate the earliest observable divergence before proposing a fix.

You are ready to continue when…

You can define the concept, draw it, build a primitive, break it, and defend a design choice using evidence.
